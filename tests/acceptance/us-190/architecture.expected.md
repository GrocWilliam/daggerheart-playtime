# Architecture

`CLAUDE.md` is the source for stack, layout and conventions; this file states the rules a change must not break.

## Layers and dependencies
- `src/routes/api/**/+server.ts` → `src/lib/server/features/*` → `src/lib/server/{db,schema,errors}.ts`.
- Pages (`src/routes/**/+page.server.ts`) read and write through the JSON API with `fetch`; they may import Zod schemas, pure rule helpers (e.g. `marksOf`, `partyDefaults`) and SRD lookups (`getSrd`, `localizedSrd`, `pickOf`, `pickOptions`, `idByName`, `adversariesByTier`, `armorGroups`) from features, never queries. The home page's direct `createCampaign`/`listCampaigns` calls are the one existing exception; add no others.
- A feature never imports another feature's helpers; shared code goes to `src/lib/server/errors.ts` or the pure `src/lib/utils/`.
- Route-local pure helpers live next to their route (e.g. `campaigns/[id]/characters/new/tunnel.ts`) with a colocated test.

## Character rules
- Game rules for characters are pure functions in `src/lib/server/features/characters.ts`, unit-tested without a database: `tierOfLevel`, `thresholdsOk`, `armorStats` (armor or unarmored), `armorEvasionModifier`, `TRAIT_ARRAY`/`traitsFollowArray`, `classStart`, `derivedStats`, `gearTierIssue`, `recomputeOnPatch`.
- Class starting values (Evasion, HP) and armor values are read from the SRD by id or English name; never copied into code.
- `POST /api/campaigns/:id/characters` stores what it is given (plus an optional tier-checked `armorId`); it computes nothing. The tunnel computes the numbers with `derivedStats` and the review shows the same values it sends.
- `PATCH /api/characters/:id` recomputes thresholds, Armor and the armor's Evasion modifier through `recomputeOnPatch` when `armorId` or `level` changes; an explicit value in the same request always wins. Max HP and Evasion are never recomputed from level or class.
- POST and PATCH share gear validation and its error texts (`gearField`, `gearTierIssue`).
- Level-up rules live in `src/lib/server/features/levelup.ts`, an extension of the characters feature: it may import `characters.ts` (rules, `characterSelect`, `characterJson`) and `srd.ts`; `characters.ts` never imports it. Pure functions (`SLOTS`, `planLevelUp`, `checkLevelUp`, `applyLevelUp`, `thresholdsAfter`, `eligibleCards`) are unit-tested without a database; `levelUp(id, body)` is the only writer.
- `GET /api/characters/:id/level-up` returns the plan (available options, unmarked traits after the 5/8 clearing, eligible cards, `subclassNext`); `POST` applies the whole level-up in one transaction with the character row locked (`.for('update')`), or nothing. Every refusal is 400 `{error}`; checks that depend on the row run under the lock.
- `characters.advancements` (one `{level, tier, option}` per slot spent; `proficiency` writes two) is the only record of used slots and subclass stage; `marked_traits` holds marked trait names; `proficiency` is stored, never derived from level. None of them is writable through `PATCH`; manual level edits leave them alone.
- The review of a level-up shows the values of `applyLevelUp`, the same function the POST applies.

## SRD content and its translation
- `src/lib/server/features/srd.ts` is the only code that reads `src/lib/srd/`. English data (`core/*.json`, `adversaries.json`, `environments.json`) is upstream SRD content: never edited, never holds translations.
- French SRD text lives only in `src/lib/srd/fr/<kind>.json`, one file per kind, keyed by `getSrd` id, holding only the fields in `TRANSLATED_FIELDS[kind]` with the English element's shape (core `{"en-US": s}` leaves written as plain strings). `src/lib/srd/fr/TERMS.md` is the terminology every file follows.
- `localizedSrd(kind, id, lang)` merges French over English per top-level field and reports each field's language; a missing or misshapen field falls back to English. `getSrd` returns the merged element with the same JSON shape in both languages.
- Enumerated values (adversary/environment `type`, `tier`, `trait`, `range`, `burden`, damage type, `domain`, dice, numbers, armor feature names) stay English in data and are matched in English by code; they are displayed only through catalog keys. Form values and stored references use ids or English names (`idByName`), never translated names.
- Every rendered piece of SRD text carries the `lang` of the text shown (`Line = { text, lang }`, `nameLang`); no literal `lang="en"` on SRD content. The only English block on a French page is the footer licence notice (`data-testid="srd-licence"`).
- `src/lib/server/features/srd-fr.test.ts` enforces completeness and shape of the French files.

## Encounters and battle tracking
- `src/lib/server/features/encounters.ts` owns everything stored in `scenes.encounter`: generation, budget (`evaluate`), counts, and battle state. Routes under `api/campaigns/[id]/scenes/[sceneId]/encounter`: `POST`/`PATCH`/`DELETE` on the encounter, `POST damage` (`{adversaryId, index, amount}` → `{hpHit, encounter}`), `POST hp` (`{adversaryId, index, delta}` → encounter), `POST adversaries` (`{adversaryId, count}` → 201 encounter).
- Every write that reads the stored encounter first locks the scene row (`.for('update')` in a transaction).
- `EncounterEntry.hpMarked?: number[]` holds marked HP per copy (`length === count`, each in `0..hp`). Absent means all zeros; it is written only when a copy is first marked, so unmarked encounters keep their JSON. Count changes (`PATCH`, `POST adversaries`) cut or pad it with zeros (`resizeMarks`); regeneration resets it. A copy is defeated when marked equals the SRD `hp`.
- HP maximum and damage thresholds are read from the English SRD at request time (`getAdversary(id, 'en')`), never copied into the stored entry. `damageMarks(amount, thresholds)` is the only damage-to-HP rule.
- The Build step edits counts; battle tracking (damage, ±1 HP, adding adversaries) is on the Run step only.

## UI patterns
- Every POST form uses `use:enhance={busy}` and works without JavaScript; `busy` also closes an enclosing `<dialog>` on success.
- Creation forms (campaign, scene, item, experience, domain card), the character edit form and the DM screen's scene edit form open in `src/lib/components/Modal.svelte` (`kind`, `title`, `lang`, optional `params` added to the opener and Cancel hrefs, optional `opener` (default true), optional `clear` (query parameters removed on close, with `new`), children). It renders the opener `new-<kind>` (`href="?new=<kind>"`, other params kept) unless `opener={false}`, and `<dialog data-testid="modal-<kind>">`, open when `?new=<kind>` or `form.modal === kind`. Actions behind a modal return `fail(status, { error: <catalog key>, modal: '<kind>', values })`. The DM screen's `scene-edit` modal is opened by per-scene `scene-edit-open` links (`?step=build&new=scene-edit&scene=<id>`); it is rendered only when `load` resolves that scene, and `edit` failures return `modal: 'scene-edit'` with `sceneId` and `values`. No other dialog implementation, except the `Help` popover below.
- Character creation is the tunnel at `/campaigns/:id/characters/new?step=1..4`: steps 1–3 are GET forms carrying values in the query string (step 3: the six traits and `armorId`), step 4 posts to the route's `default` action, which re-validates and calls `POST /api/campaigns/:id/characters` with the numbers from `derivedStats`. Validation lives in `firstInvalid` (reusing `createFields`, `classStart`, `traitsFollowArray`, `tierOfLevel`); errors come back as `?step=N&invalid=<field>` (`traits` names the whole trait group). Everything works without JavaScript. No server-side draft state.
- Level-up is a second tunnel at `/characters/:id/level-up?step=1..5` with pure helpers in `flow.ts` (relative imports, never imported by `+page.svelte`): GET steps carrying values in the query, errors as `?step=N&invalid=<field>`, a final POST to the `default` action that calls the API and redirects 303 to the sheet. Its validation works against the GET plan, not the database. The sheet's `level-up` link shows only below level 10 with an SRD class.
- SRD help text is shown through `src/lib/components/Help.svelte` with `lines: Line[]`.
- Help panel: `Help.svelte` uses the native Popover API only: a `help-open` `<button type="button" popovertarget>` and a `popover="auto"` `<span data-testid="help-panel">` (id from `$props.id()`) closed by `help-close` (`popovertargetaction="hide"`). No click handler, no dependency, not `Modal`. Markup is inline-level only (`span`, `strong`, `button`). With a `label` prop the trigger shows that label (dotted underline) and the label is not repeated before it; every helper that follows a visible label uses it, and "?" is only for helpers inside prose. The accessible name stays `"<help.label> <name>"`. The panel looks like the `Modal` panel. One panel is open at a time.
- Inline on purpose: journal quick add, encounter Generate, loot Roll, battle damage/HP/add on the Run step.
- Character sheet tabs: `/characters/:id?tab=play|traits|gear|cards|notes`, parsed by `parseTab` in `src/routes/characters/[id]/tabs.ts` (unknown or missing → `play`). Tabs are plain links; only the current tab is rendered; no tab state in JavaScript. Every sheet action is posted through `actionHref(name, tab)` (`?/<name>&tab=<tab>`, from `ACTION_TAB`), redirects 303 to `?tab=<tab>` without JavaScript, and on failure returns `section` (from `ACTION_SECTION`) so the alert shows inside that section. A new sheet action must be added to both maps (`tabs.test.ts`).
- Character rows are shared components, used by the sheet and the Run cards: `Tracker`, `DefenseLine`, `ConditionBadges`, `DamageForm`. `Tracker` is a 3-column grid (`6rem` label column, a nowrap stepper, `Pips`), so the − buttons and pips of trackers in one container line up within 1px. Fear uses `Tracker variant="band"`. Don't copy their markup into a page.
- Forms carry no box: the global `form` rule only sets a bottom margin. The surface card look (surface background, `3px double` accent border, `0.5rem` radius) belongs to `article`, `encounter-adversary` and `loot-entry` cards, `sheet-panel` and the `Modal` panel only. A one-field form is one flex row (`flex flex-wrap items-end gap-2`).
- Selects listing SRD names on the DM screen use `<option value={id} lang={nameLang} label={name}></option>` (empty body), so page text never contains other adversaries' or environments' names.
- Layout is mobile first with `md:` (768px) and `lg:` (1024px) only, plus `min-[600px]:` for the modal size; no `max-width` queries. Every page has no sideways scroll and 44×44 px targets at 360, 375, 768, 1024 and 1180 px wide; nothing depends on hover.
- Button variants: every `<button>` and button-styled link has exactly one of `btn-primary`, `btn-secondary`, `btn-ghost`, `btn-danger`, defined once in `@layer components` in `src/app.css`. At most one `btn-primary` per form. Every delete or remove action is `btn-danger`. Steppers and Move up/down are `btn-ghost`. Toggles use `aria-pressed`; pressed looks primary. Button groups sit in `flex flex-wrap gap-2`. The base `button` and `a` rules live in `@layer base`, so variants beat them and utilities beat variants. `src/buttons.test.ts` enforces one variant per button.
- Tokens: `--border` is written `--alpha(var(--accent) / 35%)`, never as a colour function in `src`. No palette colour beyond the seven palette variables and `--border`.
- Tab bars: `step-*` and `sheet-tabs` are 44px links on a `--border` bottom line. The current tab (`aria-current`, `step` on `step-*` and `page` on `sheet-tabs`, as today) has an accent background and bg-coloured text. `sheet-tabs` scrolls inside itself (`overflow-x: auto`) when it does not fit.
- Layout breakpoints: mobile first with `md:` and `lg:`, `min-[600px]:` for the modal only, and the Run step's 80rem body width from 1280px (`body:has([data-testid=run])` in `app.css`) only.
- Disclosures: disclosures are native `<details>`. On the Build step each scene's `scene-more` is closed, except on the current scene. Everything works without JavaScript.

## Data model
Campaigns, characters (with items, experiences, cards, proficiency, advancements jsonb, marked_traits jsonb), scenes (encounter jsonb including per-copy `hpMarked`, loot jsonb), journal entries. Stored SRD references are ids or English names. Schema changes follow `CLAUDE.md` (Drizzle, `drizzle/`, frozen `migrations/`); jsonb shape changes need no migration but must keep older stored values readable (new fields optional, absent = default).
